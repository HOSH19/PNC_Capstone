# 설계 의사결정 기록 (기술면접 대비)

> 은행 리스크 스코어링 파이프라인을 만들며 실제로 내린 결정들과 그 근거.
> 각 항목은 **문제 → 고려한 선택지 → 결정 → 근거 → 면접 포인트** 구조.
> "면접에서 이렇게" 줄이 핵심 — 그 결정에서 뽑아낼 수 있는 일반 원칙이다.

---

## 1. 데이터 소스 선정

### 1.1 소스 선정 기준을 3개 질문으로 프레임화

- **문제**: 후보 데이터 소스가 17개. "좋아 보이는 것"을 다 넣으면 모델이 흔들린다. 무엇으로 거를까.
- **결정**: 스코어링 = "과거로 학습해 은행별 미래 예측"이므로 소스마다 3개 질문을 통과해야 채택.
  1. **재현성** — 과거 시점 값을 그때 모습대로 되살릴 수 있나 (백테스트 학습 가능?)
  2. **귀속(attribution)** — 이 데이터가 어느 은행 것인지 확실한가
  3. **지속성** — 무료·안정·합법으로 계속 받을 수 있나
- **결과**: 정부 규제 데이터(FFIEC Call Report, FDIC/OCC/Fed enforcement, FDIC 실패 리스트, FDIC BankFind)를 Tier 1로, FRED·CFPB·EDGAR·GDELT를 Tier 2로, 나머지는 제외.
- **면접에서 이렇게**: "데이터 소스를 '있으니까 쓴다'가 아니라, ML 문제의 성질(지도학습 = 과거 재현 필요)에서 역산한 선정 기준을 먼저 정의했다. 판단 기준을 문서화하니 팀 내 '왜 뺐냐' 논쟁이 사라졌다."

### 1.2 뉴스 API 제외 — 진짜 이유는 쿼터가 아니라 재현성

- **문제**: NewsAPI, Alpha Vantage 등 뉴스 API에 데일리 쿼터 제한. 뺄까?
- **함정**: "쿼터 때문에 제외"는 약한 근거 — 캐싱·스케줄링으로 우회 가능하다.
- **결정**: 진짜 근거는 **과거 복원 불가**. NewsAPI 무료 티어는 lookback 약 1개월 → 2019년 기사를 못 꺼내니 백테스트 학습 자체가 불가능. 여기에 상업 라이선스 제약, 은행 귀속 노이즈가 겹쳐 제외.
- **면접에서 이렇게**: "표면 이유(rate limit)와 본질 이유(historical reproducibility)를 구분했다. 엔지니어링으로 우회 가능한 제약과 문제의 본질을 흔드는 제약은 다르게 다뤄야 한다."

### 1.3 텍스트 데이터만 스코어링 대상

- **문제**: 재무·매크로·주가·불만 건수까지 전부 "스코어링"해야 하나?
- **결정**: 스코어링 = **텍스트 → 감성 신호 변환**. 이미 숫자인 데이터(Call Report, FRED, CFPB 건수, 주가)는 변환이 필요 없으므로 스코어링을 건너뛰고 다운스트림(대시보드/리스크 모델)에서 감성점수와 조인.
- **면접에서 이렇게**: "'신호를 추출해야 하는 데이터'와 '이미 신호인 데이터'를 구분했다. FinBERT는 텍스트를 숫자로 바꾸는 앞단일 뿐, 구조화 데이터는 그 변환을 거칠 이유가 없다."

## 2. 모델링 방법론

### 2.1 LLM 라벨링 → FinBERT 파인튜닝 (지식 증류)

- **문제**: 감성 라벨이 붙은 학습 데이터가 없다. 매일 수만 건을 무엇으로 채점하나?
- **고려한 선택지**: (a) pretrained FinBERT 그대로 사용, (b) 매일 LLM으로 직접 채점, (c) LLM으로 라벨 생성 → 작은 모델 파인튜닝.
- **결정**: (c). Llama가 **한 번** 대량 정답지를 만들고(weak supervision), 그 라벨로 FinBERT를 파인튜닝 → 가볍고 빠른 FinBERT가 **매일** 서빙.
- **근거**: LLM은 똑똑하지만 매일 대량 추론엔 느리고 비싸다. FinBERT는 작아 CPU로도 배치 가능. "똑똑한 모델의 지능을 싼 모델로 증류(distillation)."
- **면접에서 이렇게**: "라벨 없는 문제를 LLM 기반 weak supervision + knowledge distillation으로 풀었다. 학습용(비싸도 됨)과 서빙용(싸고 빨라야 함)의 요구가 다르다는 점을 모델 2개로 분리했다."

### 2.2 서빙은 LLM이 아니라 CPU FinBERT

- **결정**: 서빙(⑥ 일 배치)은 GitHub Actions CPU 러너에서 FinBERT급 모델로. LLM API 의존 없음.
- **근거**: 매일 도는 경로에 유료 API·rate-limit·ToS 의존성을 넣지 않는다. 파인튜닝 환경(Kaggle GPU)과 라벨링 환경을 재사용해 인프라 중복 제거.
- **면접에서 이렇게**: "운영 경로(daily path)에서 외부 의존성과 비용을 제거하는 게 안정성의 핵심. 무거운 작업(파인튜닝)은 오프라인 1회로 밀어냈다."

## 3. 라벨링 품질 관리

### 3.1 사람 블라인드 검증 + champion-challenger

- **문제**: LLM 라벨을 그냥 믿어도 되나?
- **결정**: 200~300건을 클래스·소스별 층화 추출해 사람이 **블라인드**(모델 라벨 안 보고) 라벨 → LLM과 불일치 측정. 게이트 실패 시 Gemini를 challenger로 투입해 불일치 행에 리뷰 집중, 사람 일치율로 champion 선정.
- **핵심 판단**: **무작위 노이즈는 허용**(파인튜닝은 노이즈에 강건), **체계적 편향은 불가**(예: 규제 뉴스를 전부 negative로). 리뷰는 "패턴 찾기"에 집중.
- **면접에서 이렇게**: "라벨 품질을 '정확도 X%'가 아니라 '무작위 오류 vs 체계적 편향'으로 나눠 봤다. 파인튜닝이 견디는 오류와 못 견디는 오류를 구분하는 게 품질 게이트 설계의 요점."

### 3.2 라벨링 시 결과를 훔쳐보지 않는다

- **결정**: 라벨은 **기사 텍스트만으로** 부여. "이 은행이 나중에 망했나"로 판단 금지 (그 비교는 백테스트의 몫).
- **근거**: 라벨에 미래 정보가 새면 target leakage. 감성 라벨(입력 신호)과 distress 결과(정답)를 분리해야 백테스트가 정직해진다.
- **면접에서 이렇게**: "라벨링 단계와 평가 단계의 정보 경계를 엄격히 그었다. leakage는 성능을 부풀렸다가 실전에서 무너지는 대표적 함정."

### 3.3 Risk lexicon은 서술 지표일 뿐, eligibility 필터로 쓰지 않음

- **문제**: 부정 단어 사전으로 "리스크 기사"만 골라 라벨링하면 효율적이지 않을까?
- **결정**: 안 함. 중요한 리스크 기사에는 명시적 부정어가 없는 경우가 많다 ("bank explores strategic alternatives", "chief risk officer departs", "deposits fall for third consecutive quarter"). lexicon 필터는 바로 그런 기사를 걸러 버린다.
- **면접에서 이렇게**: "휴리스틱 필터가 정답 분포를 왜곡하는 사례. 눈에 띄는 신호로 미리 거르면, 정작 모델이 배워야 할 미묘한 케이스를 학습셋에서 지워버린다."

### 3.4 라벨 정의를 "리스크 방향"으로 설계 (순수 감성 아님)

- **문제**: `positive/negative/neutral` 라벨이 무엇을 재야 하나 — 글의 톤(sentiment)인가, 은행 리스크 방향인가?
- **결정**: 리스크 방향. `negative` = 리스크 상승 시사(손실·예금이탈·규제조치 + "전략적 대안 모색" 같은 완곡한 distress 신호 포함), 순수 톤이 아님.
- **근거**: 중요한 리스크 기사엔 명시적 부정어가 없는 경우가 많다("explores strategic alternatives", "CRO departs"). 순수 톤 라벨은 그런 기사를 neutral로 놓친다. 리스크 방향은 목표(부실 조기경보)와 직접 정렬되고, 그 어려운 경계는 few-shot 예시로 모델에 각인한다.
- **면접에서 이렇게**: "라벨의 정의를 '데이터에 있는 것(톤)'이 아니라 '내가 예측하려는 것(리스크)'에 맞췄다. proxy 라벨 vs target 라벨의 구분, 그리고 판단이 어려운 그 라벨을 few-shot demonstration으로 일관화한 게 요점."

### 3.5 라벨링 런타임 = vLLM (처리량이 곧 GPU 쿼터)

- **문제**: Kaggle 무료 GPU(주간 시간 쿼터)에서 수만 건의 짧고 길이 제각각인 프롬프트를 라벨링. 무엇으로 돌리나?
- **고려**: (a) transformers + 4bit, (b) Ollama, (c) vLLM.
- **결정**: vLLM. **continuous batching**(한 시퀀스가 끝나면 즉시 다음 요청을 슬롯에 채워 head-of-line blocking 제거) + **PagedAttention**(KV캐시 페이징으로 같은 VRAM에 더 큰 배치). 순수 톤은 한 단어 출력이지만 입력 길이 편차가 커서 정적 배치의 낭비가 큰데, 이걸 정면으로 해결.
- **면접에서 이렇게**: "배치 LLM 추론에서 병목은 throughput이고 그게 곧 비용/쿼터다. continuous batching과 PagedAttention이 왜 정적 배치보다 빠른지로 도구를 골랐다. 덤으로 guided decoding으로 출력을 세 라벨로 강제해 파싱/검증을 없앴다."

### 3.6 스모크 테스트로 프롬프트 갭을 잡고 고쳤다 (v1→v2)

- **문제**: 프롬프트가 실제로 리스크 방향을 잡는지, 대량·비싼 라벨링 전에 어떻게 확인하나?
- **결정**: 20행짜리 **스모크 셋**을 정답 키와 함께 설계 — 특히 톤과 리스크가 어긋나는 **적대적 함정**(완곡한 distress "전략적 대안 모색", 반전 "동의명령 해제=호재", 배당 동결=중립)을 심어 Kaggle에서 end-to-end로 파이프라인 + 라벨 품질을 동시에 검증.
- **결과**: 첫 판(v1) 19/20 — 유일한 미스가 "OCC와의 formal written agreement"를 neutral로 본 것(규제 합의를 관료적 표현으로 오독). **체계적 갭**으로 판단 → v2에 "규제기관과의 서면합의/동의명령/cease-and-desist = enforcement = negative" 명시 + few-shot 추가 → 재실행 **20/20, 회귀 없음**.
- **면접에서 이렇게**: "싼 스모크(20행)로 비싼 본 게임(수천 건 × GPU 쿼터) 전에 검증한다. 정답 키에 톤↔리스크 어긋나는 적대적 케이스를 일부러 심어 프롬프트의 체계적 약점을 드러내고, 발견된 갭을 프롬프트 버전(v2)으로 닫는 실증적 프롬프트 엔지니어링 루프를 돌렸다."

## 4. ML 엄밀성

### 4.1 시간 기반 train/validation 분할 (무작위 아님)

- **결정**: 무작위 분할 대신 시간 기반(마지막 N주 홀드아웃).
- **근거**: (1) 서빙 현실과 일치 — 실제론 과거로 학습해 미래를 예측한다. (2) 신디케이션 준중복 기사가 train/val을 넘나들며 새는 leakage 방지.
- **면접에서 이렇게**: "시계열 성격의 문제에서 무작위 split은 낙관적으로 편향된다. near-duplicate leakage까지 고려해 시간 분할을 택했다."

### 4.2 백테스트는 희소 이벤트 평가

- **맥락**: 실패 이벤트 ~3,627건 중 GDELT 시대(2017+)에 속하는 건 ~27건, 4분기 내 distress 양성은 은행-분기의 ~0.45%.
- **결정**: 백테스트를 희소 이벤트(rare-event) 평가로 설계 — accuracy가 아니라 클래스별 지표, 소수 양성에 맞는 평가.
- **면접에서 이렇게**: "0.45% 양성률이면 '전부 음성' 모델도 99.5% accuracy. 지표를 문제의 base rate에 맞춰 골랐다."

## 5. 학습/서빙 일관성 (MLOps)

### 5.1 eligibility 필터는 단 하나만 존재 (train/serve skew 방지)

- **문제**: "무엇을 채점 대상으로 볼지"(언어·노이즈 필터)를 라벨링 export와 매일 서빙이 각자 구현하면?
- **결정**: **공유 eligibility 모듈 하나**를 양쪽이 호출. 필터를 복붙하지 못하게 규칙화.
- **근거**: 두 곳이 미세하게 달라지면 "학습 때 본 분포"와 "서빙에서 채점하는 분포"가 조용히 어긋난다(train/serve skew) — 재현 어려운 버그.
- **면접에서 이렇게**: "전처리 로직 중복은 train/serve skew의 대표 원인. single source of truth로 두고 양쪽이 import하게 강제했다."

### 5.2 단일 작성자(single-writer) 규칙

- **결정**: `item_score`·`finbert_status`는 서빙 배치만, `item_label`은 import 스크립트만 쓴다. 소비자는 읽기 전용.
- **근거**: 여러 주체가 같은 테이블을 쓰면 경합·불일치. 쓰기 주체를 하나로 고정하면 상태 추론이 단순해진다.
- **면접에서 이렇게**: "테이블별로 writer를 하나로 못박아 동시성·정합성 문제를 설계 단계에서 제거했다."

## 6. 데이터 엔지니어링 / 스키마

### 6.1 item_label vs item_score — 수명주기가 다르면 테이블을 나눈다

- **결정**: 라벨은 (아이템 × 라벨러)당 한 행으로 **이력** 보존(champion·challenger·human 공존), 점수는 아이템당 **최신 한 행**. 두 개의 테이블.
- **근거**: 하나는 append-only 이력, 하나는 latest-only 상태. 수명주기가 달라 한 테이블에 억지로 담으면 둘 다 어색해진다.
- **면접에서 이렇게**: "테이블 분리 기준을 '엔티티'가 아니라 '수명주기(history vs latest)'로 봤다."

### 6.2 CHECK 제약 vs enum — 확장을 한 줄 마이그레이션으로

- **결정**: `source`, `label_source` 같은 값 집합을 DB enum이 아니라 `CHECK (... IN (...))`로.
- **근거**: 라벨러/소스 추가가 잦다. enum ALTER는 무겁고, CHECK는 "제약 drop 후 재생성" 한 줄 패턴으로 끝난다.
- **면접에서 이렇게**: "확장 빈도가 높은 값 집합은 enum보다 CHECK가 운영상 가볍다는 트레이드오프를 택했다."

### 6.3 신디케이션 중복 접기 (title_hash)

- **맥락**: 같은 기사가 여러 도메인으로 복붙 유입. GDELT 유입의 상당수가 중복.
- **결정**: 정규화 제목 해시(`title_hash`)로 삽입 전 중복을 한 행으로 접고(`n_duplicates`에 카운트), overlap 재조회로 다른 URL로 다시 온 같은 기사도 제거.
- **면접에서 이렇게**: "외부 소스의 중복은 unique key만으로 안 잡힌다(같은 기사가 다른 URL로 옴). 콘텐츠 기반 해시로 dedup했다."

### 6.4 마이그레이션 번호 충돌 해결 (007 → 011)

- **문제**: 내 브랜치와 병렬 PR이 동시에 `007_*` 마이그레이션을 만들어 번호 충돌.
- **결정**: PR이 007~010을 점유하므로 내 것을 **011로 renumber**. PR 머지 후 rebase → 파일 rename + CHECKSUMS 재생성 + 문서 참조 일괄 교체, 스키마 내용은 무변경.
- **근거**: 마이그레이션 번호는 유일·순차여야 한다. 충돌을 방치하면 실행기가 한쪽을 건너뛰거나 깨진다.
- **면접에서 이렇게**: "병렬 개발에서 흔한 마이그레이션 번호 충돌을, 내용은 그대로 두고 번호·참조·체크섬만 정합화해 해결했다. CHECKSUMS로 무결성을 검증했다."

## 7. 일하는 원칙

### 7.1 데이터 안 보고 필터 짜지 않기 (노이즈 predicate 지연)

- **문제**: 13F/holdings 스팸(GDELT의 ~14%) 필터를 지금 짤까?
- **결정**: 스팸 인식 규칙은 **실제 데이터 분포를 본 뒤** 확정. v1엔 호출 지점(훅)만 두고, predicate는 export dry-run 이후 튜닝.
- **근거**: 안 보고 지어낸 필터는 진짜 스팸을 놓치고 멀쩡한 기사를 버린다. 언어 필터(이미 저장된 값만 읽음)로 뼈대를 세우고 노이즈는 데이터 기반으로.
- **면접에서 이렇게**: "필터·휴리스틱은 실제 분포를 보고 나서 짜야 정확하다. 인터페이스(자리)는 먼저, 규칙은 데이터가 말해줄 때. 근거 없는 조기 최적화를 피했다."

### 7.2 6단계 export 퍼널 (총량이 아니라 단계별 카운트)

- **결정**: 코퍼스 집계를 **수집 총량 → 고유 → 영어 적격 → 은행 관련 → 이벤트 관련 → 라벨링 최종**의 6단계로 보고.
- **근거**: 총량만 보면 소스 간 중복이 가려진다. 단계별 카운트가 실제 작업셋 크기를 드러낸다.
- **면접에서 이렇게**: "데이터 파이프라인은 '몇 건 들어왔나'가 아니라 '각 단계에서 얼마가 남나(퍼널)'로 봐야 병목과 중복이 보인다."

## 8. 시스템 아키텍처 & 구현

### 8.1 테스트 가능한 코어 vs 환경 의존 글루 분리

- **문제**: 라벨링·서빙·export/import 코드가 GPU(Kaggle)·DB(Supabase)에 의존해 CI에서 그대로 못 돌린다. 그럼 테스트를 포기하나?
- **결정**: 각 스크립트를 **순수 로직(dict in/out, 부작용 없음)** 과 **환경 글루(GPU·DB·파일 I/O)** 로 분리. 순수 로직만 pytest로 검증(eligibility 판정, 프롬프트 렌더, 라벨 검증, export 퍼널·dedup, 라벨 파싱), GPU/DB 글루는 얇게 두고 수동 스모크로 검증.
- **면접에서 이렇게**: "외부 의존성 때문에 테스트를 포기하는 대신, 결정 로직을 순수 함수로 뽑아 CI에서 돌리고 환경 글루는 최소화했다. 못 돌리는 부분(GPU)은 정직하게 수동 스모크로 분리 — TDD 커버리지와 현실을 둘 다 지킴."

### 8.2 런타임 배치 — 워크로드 성격에 플랫폼을 맞춤

- **결정**: 매일·자동·CPU면 되는 것(인제스트, 서빙)은 **GitHub Actions cron**, 가끔·수동·GPU가 필요한 것(라벨링, 파인튜닝)은 **Kaggle 무료 GPU**.
- **근거**: 무료 CI 러너엔 GPU 없음 + 라벨링/학습은 매일이 아니라 주기적 → 스케줄 불필요. 채점(FinBERT)은 CPU로 충분해 매일 cron이 맞음.
- **면접에서 이렇게**: "실행 위치를 워크로드 3축(GPU vs CPU / 매일 vs 가끔 / 자동 vs 수동)으로 갈랐다. 비싼 GPU 작업은 오프라인·수동으로 밀어내고, 운영 경로는 싸고 자동으로 유지."

### 8.3 CSV 왕복 계약으로 수동 GPU 단계를 디커플

- **결정**: 라벨링 루프를 `export(DB→CSV) → Kaggle Llama(CSV→CSV) → import(CSV→DB)`로, 두 CSV 스키마를 **고정 계약**으로.
- **근거**: 자동화 어려운 수동 GPU 단계(Kaggle)를 파일 계약으로 격리해 파이프라인이 그 단계를 몰라도 되게 함. 계약이 먼저 고정돼 팀원이 다른 조각(대시보드·백테스트·다른 라벨러)을 **병렬로** 붙일 수 있음.
- **면접에서 이렇게**: "자동화하기 힘든 수동 GPU 단계를 파일 계약으로 격리해 시스템에서 디커플했다. 인터페이스(CSV 스키마)를 먼저 고정하니 나머지가 병렬화됐다."

## 한 장 요약 (면접 엘리베이터 피치)

> 은행 리스크 조기경보를 위해, 뉴스·공시 텍스트를 감성 신호로 변환하는 파이프라인을 설계했다.
> 라벨 데이터가 없어 **LLM으로 라벨을 생성하고 그 지능을 작은 FinBERT로 증류**해, 무거운 추론은 오프라인 1회, 매일 서빙은 CPU로 처리했다.
> 데이터 소스는 **재현성·귀속·지속성** 세 기준으로 걸러 정부 규제 데이터를 축으로 삼았고, 뉴스 API는 rate-limit이 아니라 **과거 재현 불가** 때문에 뺐다.
> ML 엄밀성으론 **시간 기반 분할**로 leakage를 막고, **희소 이벤트**에 맞춰 백테스트를 설계했으며, **단일 eligibility 필터**로 train/serve skew를 원천 차단했다.
> 구현은 **순수 로직 / GPU·DB 글루를 분리**해 CI에서 TDD를 유지했고, **20행 스모크 테스트**로 프롬프트를 v2까지 실증 튜닝(20/20)했다. 자동화 힘든 수동 GPU 단계는 **CSV 왕복 계약**으로 격리해 팀이 병렬로 붙게 했다.
