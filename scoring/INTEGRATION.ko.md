# INTEGRATION — scoring 파이프라인에 연동하는 법 (쉬운 풀이판)

> 팀 공유용 정본은 영어 원본 [INTEGRATION.md](INTEGRATION.md).
> **이 한국어본은 내 이해를 위한 쉬운 풀이판**이라 표현이 더 느슨하다 —
> 정확한 계약(테이블·컬럼·enum 값)은 영어본 / [DESIGN.md](DESIGN.md) /
> `db/migrations/011_scoring_tables.sql`이 기준.

**상태: 아직 뼈대만 있는 문서 (프레임워크 코드는 미구현).** 큰 그림은
Jiwon이 프레임워크(기사 뽑아내는 export/import 스크립트, 걸러내는
eligibility 모듈, 매일 채점하는 서빙 배치, 품질 검증 하네스)를 만들고,
나머지 팀원은 아래 4가지 방법 중 하나로 거기에 **끼워 붙는다**. 문서에
*(TBD)* 로 표시된 스크립트 이름은 프레임워크가 구현되면 확정된다. 단
**데이터가 오갈 규칙(계약)은 지금 이미 확정**되어 있다(마이그레이션 `011`).

## 쉬운 개요 (먼저 읽기)

**핵심 오해 주의:** LLM(Llama)이 FinBERT를 *직접* 가르치는 게 아니다.
Llama는 기사에 정답 라벨(긍/부/중)을 **대량으로 붙이는 채점 알바**이고,
FinBERT는 그 라벨 붙은 기사를 **교재 삼아 파인튜닝되는 학생**이다.

왜 모델을 둘이나 쓰나 — 역할이 다르기 때문:

| | Llama (LLM) | FinBERT |
|---|---|---|
| 속도/비용 | 느리고 무거움 | 작고 빠름, **CPU로 매일 배치** |
| 역할 | **한 번** 정답지 대량 생성 | **매일** 새 기사 채점 |

즉 "똑똑한 Llama가 한 번 가르치고 → 가볍고 빠른 FinBERT가 매일 실무를
뛴다." 매일 수만 건을 LLM으로 돌리면 느리고 비싸서, 그 지능을 싸고 빠른
FinBERT로 **증류(distill)**해 옮기는 구조다.

```
① 기사 수집 (GDELT, EDGAR 등 → raw_item)
      ↓
② 걸러내기 (eligibility): 영어만, 스팸 제거 → 채점 대상만 추림
      ↓
③ Llama 라벨링: 각 기사에 긍/부/중 정답 부여        ← 채점 알바
      ↓
④ 사람이 200~300건 블라인드 검증: 라벨 신뢰도 확인   ← 품질 게이트
      ↓
⑤ FinBERT 파인튜닝: 검증된 라벨로 학습              ← 학생이 공부
      ↓
⑥ 매일 배치 서빙: FinBERT가 새 기사 채점 → item_score
      ↓
⑦ 대시보드: 감성점수 + 재무(fundamentals) + 규제조치 조인
```

**이 문서(아래 A~D)는 이 흐름 설명서가 아니라, 팀원이 이 흐름의 어디에
어떻게 끼어드는지를 정하는 연결 가이드**다. 각 패턴이 붙는 지점:
A → ③, B → ①·②, C → ⑦, D → ④.

## Step 0 — 나는 어떤 방식으로 붙나 (골라보기)

- **기사를 채점할 모델이나 프롬프트가 있다** (Gemini, Qwen, 내가 고친 Llama
  프롬프트) → **패턴 A: 채점자(라벨러) 한 명 더 추가.** 흐름 ③에 낀다.
- **새 데이터 소스를 붙였고, 그 기사들이 점수를 받게 하고 싶다** →
  **패턴 B: 소스 어댑터 등록.** 흐름 ①→② 사이. **주의: 수집만 해서는 절대
  자동으로 채점되지 않는다** — 등록 안 하면 그 소스 기사는 영영 "대기중
  (`pending`)"에 방치된다.
- **점수를 읽어서 뭔가 만들고 싶다** (백테스트, 대시보드 등) →
  **패턴 C: 소비자.** 흐름 ⑦. `item_score`를 **읽기만** 한다.
- **라벨 손검증을 부탁받았다** → **패턴 D: 블라인드 라벨링.** 흐름 ④.
  코드 없이 1~2시간짜리지만, 품질 검증의 정답지가 된다.

## 데이터가 오가는 규칙 (계약 — 쉬운 설명)

핵심 테이블 3개와 그 사용 규칙만 알면 된다:

- **`item_label`** = 라벨(채점 결과) 저장소. **"기사 하나 × 채점자 하나 =
  한 줄."** 같은 기사를 Llama도, Gemini도, 사람도 채점하면 각각 한 줄씩
  쌓인다. `UNIQUE (raw_item_id, label_source)` 규칙 = 같은 채점자가 같은
  기사에 두 줄을 남길 수 없다 → 재채점하면 자기 줄만 덮어쓴다.
- **`item_score`** = 최종 점수. **기사당 딱 한 줄, 최신 것만.** 여기엔
  **매일 도는 서빙 배치만 쓴다(write).** 다른 사람은 읽기만.
- **`raw_item.finbert_status`** = 그 기사가 채점됐는지 나타내는 상태 깃발.
  `pending`(대기) → `done`(완료) / `failed`(에러) / `skipped`(채점 대상
  아님). 이 깃발도 **서빙 배치만 바꾼다.**
- **라벨링은 DB 직접이 아니라 CSV를 주고받는다.** export가 "채점할 기사"를
  CSV(`labeling_batch_<날짜>.csv`)로 뽑아주면, 채점자가 라벨을 채워
  `labels_<날짜>.csv`로 돌려준다.

## 패턴 A — 채점자(라벨러) 한 명 더 추가 (예: Kaggle의 Qwen)

새 채점 모델을 파이프라인에 등록하는 것. Phase 1에서 `raw_item`에 새 소스를
추가하던 "한 줄 고치기" 리듬과 같다.

1. **마이그레이션** — `db/migrations/`의 다음 빈 번호 파일에서, 허용된
   채점자 목록(`label_source` CHECK)에 `'qwen_kaggle'`을 한 줄 추가한다.
   (`'llama_kaggle'`, `'gemini'`, `'human'`은 011에 이미 있음 → 그건 손댈
   필요 없음. 기존 011 파일은 절대 수정하지 말고 새 번호로.)
2. **프롬프트 파일** — `evals/prompts/<내이름>_<모델>.md`, 1인 1파일.
   프롬프트 버전은 DB가 아니라 이 파일로 관리한다.
3. **채점(라벨링)** — export CSV를 그대로 받아, 기사마다 정확히
   `positive|negative|neutral` 하나를 골라 `labels_<날짜>.csv`로 낸다.
   `model_meta`(JSON)에 모델 이름·양자화·프롬프트 버전·실행 날짜를 적는다.
   기준 구현인 Llama 노트북 *(TBD)* 을 복사해서 쓰면 된다.
4. **Import** — import 스크립트 *(TBD)* 를 `--label-source qwen_kaggle`로
   돌린다. 규칙상 재채점해도 **내 줄만** 덮어쓰지 남의 채점은 안 건드린다.
5. **확인** — 클래스별 개수가 상식적인지, 그리고 champion과 얼마나 갈리는지:
   ```sql
   SELECT label, count(*) FROM item_label
   WHERE label_source='qwen_kaggle' GROUP BY 1;
   -- 채점자끼리 라벨이 갈리는 기사 찾기
   SELECT raw_item_id FROM item_label
   GROUP BY 1 HAVING count(DISTINCT label) > 1;
   ```

## 패턴 B — 내 소스 기사가 점수를 받게 만들기 (예: alpha_vantage)

수집만 해두면 그 기사는 영영 `pending`에 남는다. **채점 대상으로 등록**해야
서빙 배치가 집어간다.

1. **어댑터 등록** — 공유 eligibility 모듈 *(TBD: 소스당 dict/함수 하나)* 에
   내 소스를 추가한다. 어떤 컬럼이 텍스트인지(`title`만? `title +
   text_excerpt`?), 소스 고유의 건너뛰기 규칙이 있는지. (예: Alpha Vantage는
   자체 감성 점수를 딸려 보내는데 — **무시한다.** 우리 점수에 절대 섞지
   않는다.)
2. **걸러내기 규칙을 내 스크립트에 복붙하지 말 것.** 영어-only 필터,
   스팸 제거 규칙은 eligibility 모듈 한 곳에 있고, **라벨링(⑤용 데이터
   추출)과 매일 서빙(⑥)이 같은 걸 쓴다.** 각자 복붙하면 "학습 때 본 기사
   분포"와 "실제 채점하는 기사 분포"가 조용히 어긋나서 버그가 난다. 새 규칙이
   필요하면 그 모듈에 테스트와 함께 추가한다.
3. **확인** — export dry-run *(TBD 플래그)* 이 소스별로 "채점함 / 건너뜀"
   개수를 찍어준다. 서빙 한 번 돌린 뒤 내 소스 기사가 전부 `pending`을
   벗어나야 한다 (→ `done` 또는 `skipped` + `last_error`에 이유).

## 패턴 C — 점수 읽어 쓰기 (백테스트, index, 대시보드)

**읽기 전용.** 절대 `item_score`·`item_label`에 쓰지 않는다.

- 은행 붙이기: `raw_item.bank_id`로 조인. 재무데이터 붙이기:
  `bank.fdic_cert ↔ fact_bank_quarter.fdic_cert_number` (FK 없이 값으로 조인).
- **점수 없는 기사가 있는 게 정상이다** (`skipped`/`pending`이라서). 그러니
  outer join을 쓰고, "모든 기사에 점수가 있다"고 가정하지 말 것.
- 서로 다른 시점을 비교할 땐 `model_version`으로 필터/그룹핑. 다른 버전의
  FinBERT가 낸 점수끼리는 직접 비교 못 한다 (채점 기준이 다르니까).

## 패턴 D — 블라인드 손검증 (전원, 1인당 ~100~150건)

Llama 채점이 믿을 만한지 사람이 확인하는 단계(흐름 ④).

1. 게이트 담당자가 샘플 CSV를 준다. **모델 라벨은 안 적혀 있다** — 그래서
   "블라인드". 어딘가 찾아보지도 말 것.
2. **기사 텍스트만 보고** 라벨을 단다. "이 은행이 나중에 망했나"로 판단하면
   안 된다 (멘토 지시 — 그 비교는 백테스트의 몫). 순수하게 글의 톤만 본다.
3. 돌려주면 `label_source='human'`으로 들어간다. 사람 라벨은 학습셋에서
   Llama 라벨을 **덮어쓰기** 때문에, 대충 찍은 라벨은 곧바로 학습을 망친다 —
   정말 헷갈리면 찍지 말고 `neutral`.

## 다 됐다고 볼 기준 (Definition of done)

- **패턴 A**: CHECK 마이그레이션(새 번호) + `evals/prompts/` 프롬프트 파일 +
  import 완료(클래스별 개수 눈으로 확인) + champion 불일치 쿼리 확인.
- **패턴 B**: eligibility 모듈에 어댑터 + 테스트 등록 + export dry-run 개수
  확인 + 서빙 후 내 소스에 `pending` 남은 게 0.
- **패턴 C**: 읽기만 / outer join / `model_version` 처리.
- **패턴 D**: 블라인드로 / 텍스트만 보고 / 기한 내 제출.

## 전원 공통 규칙 (사고 방지용)

- **쓰는 사람은 정해져 있다.** `item_score`·`finbert_status`는 서빙 배치만,
  `item_label`은 import 스크립트만 쓴다. 그 외엔 아무도 이 테이블에 안 쓴다.
- **걸러내기(eligibility) 로직은 딱 하나만 존재한다.** 언어·스팸 필터를 내
  스크립트에 복붙하고 있다면 멈춰라 — 학습/서빙이 어긋나는 버그 공장이다.
- **채점자는 결과를 훔쳐보지 않는다.** 기사 텍스트 넣고, 감성만 뽑는다.
- 저장소 공통 규칙(`CLAUDE.md`) 적용: 작은 단위로 진행, 계획에 없는
  의존성·테이블·enum 값은 먼저 물어보고 추가.
- 막히면 물어볼 순서: [DESIGN.md](DESIGN.md) → `011` 헤더 주석 → 팀 채널.
  다섯 번째 패턴을 발명하기 전에 먼저 물어볼 것.
